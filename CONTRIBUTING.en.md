# Contributing to GIS WorkTable

Thank you for helping improve GIS WorkTable. Contributions should address a reproducible user problem and include evidence for the behavior they change.

## Before opening an issue

For a bug report, include the operating system, steps to reproduce, expected and actual behavior, the relevant coordinate reference system and units, and a small sample dataset when you can share it safely. Remove API keys, credentials, browser storage, private conversation history, and data you are not allowed to redistribute.

For a feature proposal, describe the user, the GIS task, the current obstacle, and an observable acceptance result. Note any external service, model, credential, or data dependency.

## Changes and pull requests

Keep a change focused. A pull request should explain:

- the problem and its cause;
- the user-visible behavior before and after the change;
- the checks performed and their results;
- compatibility effects and any remaining limitations;
- related issues and the sources or licenses for third-party code, data, and assets.

Follow the repository's existing structure and add or update tests when the behavior changes. If a check cannot be run, state why and do not describe it as passing. Distinguish mocked tests from real model, online-service, browser, desktop, or clean-install validation.
