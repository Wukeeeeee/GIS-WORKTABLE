# AI 对话与工具延迟检查

日期：2026-10-11。检查基线为 `9064ab5` 的本地工作区，操作系统 Windows，Python 3.13.0。用户反馈模型为 DeepSeek，但尚无具体慢请求、完整模型配置和阶段日志。本轮未调用真实 DeepSeek API，也未完成浏览器渲染计时；以下严格区分代码事实、本地实测和待验证项。

## 已修复的两个问题

### 1. Python 沙箱无条件初始化外部网络与绘图环境

`execute_python` 原先每次都导入 OSMnx 并依次探测最多五个 Overpass 镜像，每个请求 timeout=5；即使用户代码只有 `print(2 + 2)` 或 NumPy 运算，也会付出这个成本。另外每次都会生成并执行 matplotlib 字体初始化。

现在通过已通过沙箱检查的 AST 识别导入，仅在代码导入 osmnx 时初始化 OSM 镜像；仅在导入 matplotlib 或使用预置 `plt` 时配置绘图字体。沙箱校验、独立子进程和产物收集机制保留。

| 现有测试 | 修复前单次耗时 | 修复后定向检查耗时 |
| --- | --- | --- |
| 简单 Python 计算 | 19.10 s | 0.03 s |
| NumPy 示例 | 12.85 s | 0.16 s |
| PNG 绘图示例 | 13.05 s | 0.58 s |

这是本机不同次测试运行的观察值，不是统计充分的性能保证，也不是完整 AI 请求的提速比例。真正使用 osmnx 的任务仍可能受到镜像探测延迟影响。

### 2026-10-27 OSMnx 导入不再触发 Overpass 探测

后续执行边界审查确认：条件初始化仍会在用户代码只导入 OSMnx 时探测最多五个 Overpass 镜像，每个请求最多等待 5 秒。现在移除了这段自动探测；导入 OSMnx 本身不再发出网络请求。该变更只移除隐藏初始化，`execute_python` 仍不隔离用户代码主动执行的网络操作；获取边界和要素继续使用专用 GIS 工具。

### 2. SSE 请求准备阶段阻塞事件循环

`/api/chat/stream` 原先在 async 路由中直接调用 `_build_system_content`。开启技能路由时，内部同步等待模型，健康检查及其他请求可能随之阻塞。

现在把提示词构建移至 `asyncio.to_thread`。新增回归测试模拟路由等待，确认期间事件循环仍可处理健康检查。这个变化改善服务响应性，不会减少远程模型本身的生成时间；SSE 返回头依然要等待当前准备阶段完成。

## 尚未修改、需要继续验证的慢点

1. **额外技能路由调用**：前端预置的 `deepseek-routed` 配置开启 router；用户保存的配置可以不同。开启时，正式 Agent 前先串行调用一次当前模型选择知识模块。纯文本问答也先构建提示词，因此仍可能支付这次成本。关闭可做对照实验，但应比较方法选择和任务完成率，不建议无证据全局关闭。
2. **尚未实现正文逐 token 展示**：Agent 使用 `stream_mode="values"` 推送步骤，正文在 `done` 才交给前端。简单问答使用 `llm.invoke`，也等全文生成。SSE 不等于正文实时输出；即使总时间不变，真正的正文流式输出能减少无反馈等待。
3. **所有工具一起交给 Agent**：当前注册 127 个工具；本轮转换后的 OpenAI 工具 schema JSON 为 87,901 UTF-8 字节。无路由/无附加知识的系统提示词约 5,817 字符，构建约 1.25 ms。字节数和字符数不是 token 数；大工具目录可能增加模型输入和选择负担，但真实延迟需要模型侧计时。
4. **Agent 的多轮等待**：一个工具任务通常需要模型选择工具 → 工具运行 → 模型总结；router 开启再多一次前置调用。多工具链或“只承诺未执行”的补执行分支会继续增加轮次。不能只用纯 GIS 工具耗时预测对话耗时。
5. **图层结果集中返回**：最终 done 才返回图层；后端计算完成后仍可能等待模型总结、序列化、传输和浏览器绘制。前端尚未完成上述阶段的实测。
6. **网络超时和重试**：外部来源、模型 SDK、Agent 补执行及前端 SSE 失败后的普通接口回退都有等待或额外调用的可能，需要用请求级日志确认；不应把所有等待归因于模型或 GIS 算法。
7. **已停用额外 LLM Verifier**：当前结果检查是确定性的 `result_guard`，本轮不能把它解释成又一次模型校验延迟。

## 本地矢量工具实测

在独立 Python 进程中调用现有 `spatial_buffer` 工具，输入 EPSG:4326 的人工构造点，距离 100 米，dissolve=False；每个规模调用三次。计时包含 GeoDataFrame 构造、投影、缓冲、结果转 GeoJSON、推送与注册；不含模型、HTTP、后续 JSON 序列化与浏览器绘制。

输入点坐标：`[121.4 + (i % 100) * 0.0001, 31.2 + (i // 100) * 0.0001]`，属性 `id=i`。

| 点数 | 三次耗时（ms） | 中位耗时（ms） | pending layers JSON UTF-8 字节 |
| --- | --- | --- | --- |
| 100 | 465.55 / 32.13 / 29.00 | 32.13 | 282,356 |
| 1,000 | 289.69 / 195.58 / 192.73 | 195.58 | 2,825,166 |
| 5,000 | 1019.89 / 1091.89 / 1068.59 | 1068.59 | 14,137,406 |

首次调用可能包含冷启动开销。数据规模和几何复杂度均影响性能；这些点数据结果不能推广到复杂面叠置、栅格或任意地理区域。

本例说明：简单分析本身可能很快，但结果体积增长明显；迁移到浏览器并不能自动解决模型等待或大结果渲染。

## 下一步优先级

1. 每次请求记录准备/路由、模型每轮、工具、首个正文、结果序列化的独立耗时，并在浏览器记录接收和绘制；避免记录凭据和完整个人输入。
2. 实现正文真正流式输出，同时保留最终产物检查；先解决错误处理、协议片段过滤和取消，再上线。
3. 用真实慢请求对照 router 开/关、不同模型和工具子集；保存输入条件及成功率，不能以删掉必要上下文换取表面提速。
4. 图层结果按需或增量加载，避免为了展示预览返回全部大 GeoJSON。
5. 最后依据测量选择哪些计算迁到 Worker、哪些任务用独立本机进程；无需先重写整个架构。

AI 比手动慢并不一定表示有问题：简单确定操作适合直接工具入口，多步骤任务才可能节省用户总体操作时间。报告长、语言流畅不等于分析准确；效果应由任务完成率、方法适用性、数据来源和结果正确性评估。
