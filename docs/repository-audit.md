# 仓库盘点与参赛方向评估

核查日期：2026-10-11。代码基线：本地 `gitee-clean-history` 的 `9064ab5`；结论来自 Git 跟踪文件、静态代码、只读 SQLite 查询与 GeoLibre 官方文档。本次未重跑功能测试、未在干净环境安装、未实测 GeoLibre UI；文档列出的能力不等于现场验证通过。OCS 具体届次、赛道及规则尚未核验。

## 1. 仓库实际情况

Git 跟踪 170 个文件，工作区内这些文件合计约 8.08 MiB。这不包括 Git 历史、被忽略的缓存、虚拟环境和个人资料。目录看起来繁多与公开源码冗余是两个问题。

| 内容 | 发现 | 处理建议 |
| --- | --- | --- |
| `backend/`、`frontend/`、`desktop/` | 运行代码与测试 | 保留；按模块职责逐步拆分，不先为目录整齐大改 |
| `knowledge/`、`skills/` | `ai_service.py` 实际加载的知识与领域提示 | 保留；补索引，不能视作无用 AI 资料删除 |
| `data/gis_services.db` | 默认运行目录快照，约 2.30 MiB | 保留最小可用快照；补来源、许可、快照日期、schema 和更新流程 |
| `frontend/geosource_map.html` | 约 3.38 MiB；内联脚本含 `WORLD_GEO` 地理数据，页面有实际入口 | 保留；后续把边界数据与业务脚本拆开，声明来源和许可，避免先删除造成入口失效 |
| `frontend/samples/` | 仅 README 被 Git 跟踪，说明引用的 GeoJSON 未提交 | 添加人工构造、可分发的最小样例，并精确放行忽略规则 |

| `log.md`、`docs/PROJECT_AUDIT.md` | 与 CHANGELOG/路线图部分重复，包含阶段性结论 | 整理为带日期的开发记录；修正过时事实，不删除证据 |
| `docs/superpowers/`、历史 GeoLibre 笔记 | 设计与实现过程资料 | 作为开发档案保留，明确历史状态；README 只链接当前有效文档 |

## 2. 优先修复的事实与可复现性缺口

### 数据目录规模

本次对仓库自带数据库只读统计：`master = 2198`，`layers = 1561`。运行时 `get_db_path()` 当前也选择这份文件。旧材料中的 11,000+ 服务、18,000+ 图层不能直接用来描述此快照；不同环境可能由环境变量或同级 GeoSource 仓库选中不同快照。

建议：所有界面数量从实际数据库统计；区分“索引条目”“可检索资源”“最近探活成功”“可以下载”；给目录和演示固定快照，保存校验和及统计日期。

### 获取能力需要分级

| 数据通道 | 静态代码可确认的状态 | 当前不能直接承诺的内容 |
| --- | --- | --- |
| OSM Provider | Overpass 要素获取与矢量产物流程 | 任意区域完整覆盖、外部接口一直可用 |
| DataV / 高德 / 在线 DEM | 有对应边界、POI、高程工具实现 | 无凭据或无网络条件下全部可用 |
| GeoSource | 服务与图层索引、检索和接入入口 | 所有收录条目都有可下载原始数据 |
| Copernicus Provider | 配 token 后的目录检索；download 显式拒绝 | Sentinel 影像自动下载闭环 |
| USGS Provider | Landsat 目录发现；download 显式拒绝 | USGS 影像自动下载闭环 |
| 地理空间数据云 Provider | 提供人工获取后上传的指引 | 自动检索和下载 |

建议给结果显示明确状态：`可下载`、`仅在线展示`、`仅目录检索`、`需认证`、`人工指引`、`暂不可用`。一次失败不能伪装成下载成功；获取不支持时提供真实可用的替代路径。

### 安装与测试

- 仓库没有 Git 跟踪的 `.github/workflows/` 工作流；测试文件多不等于已建立 CI。
- `cryptography` 被凭据模块直接导入，但未在 requirements 中明确声明；FastAPI 文件上传涉及 `python-multipart`。需在干净环境检查并补齐直接依赖，不能依赖开发机恰好已安装。
- 依赖包含很多宽范围版本约束，应保存一个验收过的环境或约束文件；先完成依赖可安装性验证，再决定锁定方式。
- Windows 启动脚本优先选择 `D:\python\python.exe`；应优先当前虚拟环境/明确配置的解释器，并统一 Python 版本提示。
- `.gitignore` 全局忽略 `*.geojson`，需要针对样例目录添加例外，避免“示例说明存在但数据未发布”。
- 当前未发现版本标签，桌面 package 的 `0.1.0` 不足以证明仓库已有同名发布。

## 3. 与 GeoLibre 的当前对照

官方来源，访问日期均为 2026-10-11：

- [GeoLibre 首页](https://geolibre.app/)
- [Data Integrations](https://geolibre.app/user-guide/data-integrations/)
- [Web Services](https://geolibre.app/user-guide/web-services/)
- [AI Assistant](https://geolibre.app/user-guide/ai-assistant/)
- [开源仓库](https://github.com/opengeos/GeoLibre)

GeoLibre 文档明确介绍 STAC、Planetary Computer、Earth Engine、NASA Earthaccess、OSM Downloader、CKAN 等来源；部分入口含搜索、下载与上图。因此不能把“GeoLibre 没有资源获取”作为当前已证实差异。用户与开发者的交流可能对应不同版本或更窄的能力定义，仍有参考价值。

| 维度 | GeoLibre 官方文档 | GIS WorkTable 的方向 |
| --- | --- | --- |
| 数据接入与目录 | 有多种来源、搜索及部分下载能力 | 竞争点应是任务匹配、覆盖需求、可用性和获取成功率，而非仅有目录 |
| AI | 有模型可配置、工具调用、SQL、地图控制与可审阅操作 | 聚焦从用户需求到数据选择再到分析产物的可靠流程，需对照实测 |
| 地图与手动操作 | 有多引擎、属性、样式、处理工具和项目状态 | 学习交互一致性与可发现性；2D/3D 本身不是独占优势 |
| 计算架构 | 文档包含浏览器计算和可选侧车 | 本地 Python 生态适合已有 GIS 算法，但安装负担需要控制 |
| 可追溯性 | 文档已有工具记录、撤销和项目能力 | 数据来源到分析参数和结果的完整记录可重点打磨，但不能先宣称对方没有 |

## 4. 建议定位与验收

候选定位：**面向中文空间分析任务，把数据发现、可用性判断、获取、分析和结果检查串起来的 GIS 工作台。** 这是下一阶段要用演示与测量验证的方向，不是当前优于 GeoLibre 的既成结论。

先选择一个垂直问题，如“指定城区的公共服务覆盖分析”，而不是同时追求所有 GIS 功能。公开演示必须使用许可适当且字段、范围明确的数据；如果来自不同来源，需解释时间差、覆盖率和坐标变换。

建议优先补充：

1. 资源能力卡：数据类型、范围、时间、分辨率/比例尺、CRS、许可、账号、能否下载、最近验证时间。
2. 任务条件筛选：按 AOI、时间、数据类型、许可和访问条件选择来源；对不适用的数据给出依据。
3. 一条真实获取闭环：选择少量稳定来源，完成搜索 → 用户确认 → 获取或在线加载 → 检查 → 分析 → 导出；明确“加载服务”与“下载原始数据”的差别。
4. 可复现任务记录：来源标识/URL、获取时间、数据文件校验和、工具参数、CRS/单位、输出清单。重跑失败时显示外部状态变化。
5. 可比较的验收集：同一组任务、区域和输入条件，对比完成率、步骤数、耗时、失败恢复、结果正确性与人工干预次数。网络与模型配置必须记录，目录数量不能代替这些指标。

## 5. 实施顺序

1. **仓库可交付**：整理有效文档入口、补示例、修正规模与能力说明、干净环境安装、基本 CI。
2. **主流程可靠**：围绕一个用户场景贯通数据获取和分析，改善失败提示及恢复路径，保存来源与参数。
3. **证明差异**：对照 GeoLibre 同条件实测；只展示能证实的强项，明确不足。
4. **参赛材料**：按 OCS 正式规则准备固定版本、视频/PPT、架构、开源来源和贡献说明。

本轮不删除或移动业务文件，不改 Git 历史，不推送。下一步整理应先处理可复现性与文档冲突，再考虑模块拆分。暂不建议为了功能表扩张而新增多渲染引擎、移动端或通用插件市场。
