# 更新与发布流程

## 日常修改

1. 确认修改范围，按 [贡献指南](../CONTRIBUTING.md) 验证。
2. 同步使用文档、示例和接口说明；用户可见变化加入 [CHANGELOG](../CHANGELOG.md) 的 `[Unreleased]`。
3. 使用 PR 模板记录问题、行为变化、验证及限制，由维护者审阅后合入。

这里是约定，不代表已有强制执行的 CI 或分支保护。

## 版本约定

- 标签使用 `vMAJOR.MINOR.PATCH`，版本正文使用 `MAJOR.MINOR.PATCH`。
- `0.x` 表示仍在演进的早期版本；在该阶段，有破坏兼容的变化提升次版本并明确迁移方式，兼容修复提升修订版本。
- 达到 `1.0.0` 后：破坏兼容提升主版本，兼容新能力提升次版本，兼容修复提升修订版本。
- 预发布使用例如 `v0.2.0-rc.1`；这里只规定格式，不承诺下一版版本号或发布日期。
- 只有实际发布桌面包时才同步 `desktop/package.json` 及对应锁文件版本。仓库发布、桌面包版本与后端接口演进应在 Release 中说明关系。

## 正式发布检查

1. 选择明确的提交，确认不混入未提交文件。记录提交号、Python/Node/操作系统、验证命令及通过/跳过/失败情况。
2. 在干净环境按 README 安装启动；分别验证无模型的手动流程，以及已配置模型的 AI 流程。外部数据源验证注明时间和服务。
3. 手动检查导入 → 分析 → 地图展示 → 导出 → 历史重跑；前端改动检查 2D/3D 同步；桌面包单独验收。
4. 核对依赖、许可证、第三方数据来源及公开材料中的脱敏情况。截图与性能指标应对应本次发布状态。
5. 将本次 `[Unreleased]` 条目移动到实际版本和发布日期下，保留新的空 `[Unreleased]`；写明不兼容变化、迁移步骤及已知限制。
6. 维护者确认发布范围后创建标签及 GitHub Release，关联源码、安装说明和已验收的产物。未生成的安装包或未验收的平台不能列为已提供。

## Release Description 模板

```markdown
## 本次变化
- 具体使用场景及改后行为

## 安装与升级
- 对应版本的操作步骤
- 兼容性影响与迁移办法（如有）

## 验证
- 提交：
- 环境：
- 命令与结果：
- 手动验收及外部服务检查时间：

## 已知限制
- 仍未支持或需要用户关注的具体行为
```

不将“准备发布”“测试曾通过”写成“已经发布”“此版本全部通过”。
